# 推理优化

## 一句话定义

这条轨道覆盖"如何高效地运行训练好的 LLM"——从量化、蒸馏到 serving 架构，追踪部署侧的技术演进。推理优化的驱动力是**成本**：LLM 的推理成本在商业部署中往往超过训练成本，每降低一个量级的推理成本，就打开一类新的应用场景。

## 演进脉络

### 阶段 1：基础推理优化（2020-2022）

LLM 大规模部署的初期，推理的主要挑战是**内存**和**吞吐量**。GPT-3（175B）在 FP32 精度下需要约 700GB 显存，远超单卡，必须靠模型并行切分到多张 GPU 上。这个阶段的工程重点是把"让模型跑起来"这个基本问题解决掉。

**混合精度推理**是第一个普及的优化：将模型权重和激活从 FP32 降到 FP16 或 BF16（BF16 在数值稳定性上优于 FP16，被大多数现代模型采用），在几乎不影响质量的前提下把内存需求和计算量各缩减约一半。

**KV Cache** 是自回归推理的核心工程问题。在自回归生成时，每生成一个新 token，都需要计算它与所有前驱 tokens 的 attention。朴素实现需要对所有前驱重新计算 K 和 V——KV Cache 把每个 token 的 K 和 V 存下来，后续步骤直接读取，避免重复计算。代价是内存：对于长序列或大批次，KV Cache 可以消耗比模型权重本身更多的显存。管理 KV Cache 的增长是长上下文推理的核心工程挑战。

**模型并行**（Tensor Parallel、Pipeline Parallel、Sequence Parallel）使超大模型可以分布在多卡上推理。Megatron-LM（NVIDIA，2019-2020）建立了 Tensor Parallel 的主流实现框架：把矩阵乘法沿行或列方向切分，各 GPU 计算一部分，再 AllReduce 合并。Pipeline Parallel 把模型的不同层放到不同设备上，用微批处理（micro-batching）填充流水线气泡。

### 阶段 2：量化与蒸馏成熟（2022-2024）

这个阶段的主旋律是把模型"压缩"到更小的形态，使更多硬件可以运行它，同时降低每次推理的计算量。

**训练后量化（Post-Training Quantization, PTQ）**

量化是把模型权重从 FP16（2 字节/参数）压缩到 INT8（1 字节）或 INT4（0.5 字节），从而大幅降低内存和带宽需求。早期量化主要面向 CNN，LLM 的量化难度更高，因为 LLM 权重中存在少量"异常值"（outliers）——分布极端的值，会导致量化误差在这些位置放大，严重影响质量。

**GPTQ**（Frantar et al., 2022 年 10 月，arXiv 2210.17323）是第一个实用的 LLM 权重量化方法：用 Hessian 矩阵近似确定哪些权重对输出影响最大，优先保留精度，大幅降低了量化误差。支持 INT4 甚至 INT3，65B 模型可以在 4×RTX 3090 上运行。**AWQ**（Lin et al., 2023，arXiv 2306.00978）进一步改进：发现只需要保护约 1% 的"显著权重"（salient weights）就能维持大部分质量，这 1% 用更高精度存储，其余用 INT4。AWQ 的量化质量优于 GPTQ，且推理速度更快。

**GGUF**（llama.cpp 项目，Georgi Gerganov，2023 年）是面向 CPU 和边缘设备的量化格式，支持多种混合精度方案（Q4_K_M、Q5_K_M 等）。llama.cpp 使得大型 LLM 在普通笔记本电脑（甚至手机）上运行成为可能，是开源生态推动 LLM 普及化的核心工具之一。

**知识蒸馏（Knowledge Distillation）**

蒸馏是用大模型（teacher）的输出训练小模型（student），使小模型在更小的参数量下逼近大模型的能力。有两条路线：（1）**响应蒸馏（Response Distillation）**：用大模型的输出作为小模型的 SFT 训练数据——这是最简单的形式，也是合成数据方法的本质；（2）**Logit 蒸馏**：让小模型直接模拟大模型的输出概率分布（soft label），而不只是最终 token——这比只学习答案携带更多信息，特别是在高置信度分布的情况下。

DeepSeek-R1-Distill 系列（2025 年 1 月）是推理能力蒸馏的最重要实例：用 R1 的思维链作为 SFT 数据，把推理能力蒸馏进 1.5B-70B 的小模型，部分蒸馏版本在推理任务上超过了规模相当的直接 RL 训练模型。

**vLLM 与 PagedAttention：serving 效率的范式转变**

**vLLM**（Kwon et al., UC Berkeley，2023 年 6 月，arXiv 2309.06180）是这个阶段推理 serving 领域最重要的工程进展。问题背景：在生产 serving 场景下，不同请求的输出长度不同，预先为 KV Cache 分配足够大的内存会导致大量内存浪费（内存碎片化），严重限制系统吞吐量。

**PagedAttention** 借鉴操作系统虚拟内存的页表思想：不预先分配连续的 KV Cache 内存块，而是把 KV Cache 切成固定大小的"页"（非连续的），通过页表管理这些页的分配和回收，按需分配、用完即还。结合**连续批处理（Continuous Batching）**（不等一批请求全部完成再开始下一批，而是有请求完成就立即把新请求加入），vLLM 的吞吐量比朴素 Hugging Face 实现高 24 倍。vLLM 迅速成为开源 LLM serving 的事实标准。

**参考**：[GPTQ (arXiv 2210.17323)](https://arxiv.org/abs/2210.17323)，[AWQ (arXiv 2306.00978)](https://arxiv.org/abs/2306.00978)，[vLLM / PagedAttention (arXiv 2309.06180)](https://arxiv.org/abs/2309.06180)

### 阶段 3：推理架构创新（2024-至今）

这个阶段的技术演进方向分化：一方面是继续压榨硬件效率（推测解码、解耦推理），另一方面是应对推理时扩展（reasoning 模型）带来的根本性新挑战。

**推测解码（Speculative Decoding）**

自回归生成的一个内在限制是：每个 token 必须串行生成，无法并行化（因为下一个 token 依赖于前一个）。推测解码（Leviathan et al., Google Brain，2023 年，arXiv 2211.17192）通过引入**草稿模型（draft model）**突破这个限制：

1. 用一个小的草稿模型快速生成 γ 个候选 token（串行但很快）
2. 将这 γ 个 token 一起喂给大的目标模型做并行验证
3. 目标模型逐位验证：接受则保留，不接受则在该位置重新采样，后续候选作废

关键性质：这个过程不改变目标模型的输出分布——最终生成的每个 token 的概率分布与直接用目标模型采样相同，只是速度更快（当草稿模型的命中率高时，平均一次目标模型前向传播可以接受多个 token）。实践中，对于代码生成、结构化输出等重复模式多的任务，推测解码可以实现 2-5x 的速度提升。

**分离式推理（Disaggregated Inference）**

LLM 推理分为两个阶段：**Prefill**（处理输入 prompt，一次并行计算，计算密集型）和 **Decode**（逐 token 生成输出，内存带宽密集型）。这两个阶段对硬件的要求完全不同：Prefill 像一个大矩阵乘，充分利用 GPU 的计算单元；Decode 每步的计算量极小但需要频繁读取权重，是内存带宽瓶颈。

传统实现把两个阶段放在同一个 GPU 上，导致两个阶段互相竞争资源。分离式推理把 Prefill 和 Decode 放到不同的硬件实例上，针对各自的瓶颈独立优化。PD 分离（2024 年以来，Mooncake 等系统率先在生产中应用）使长上下文推理和高并发请求下的成本效率显著提升，是头部推理服务商的主流架构选择之一。

**推理时扩展与 serving 的根本张力**

推理时扩展（o1/o3/Claude 3.7 推理模式）为 serving 层带来了结构性新挑战。传统 serving 优化的目标是：**最大化吞吐量、最小化时延**，每个请求的计算量是已知的（固定的上下文长度）。推理模型让这两个假设都失效：

- **计算量不确定**：推理 token 数依赖于问题难度，从几百到几万 tokens 不等，难以提前调度
- **时延可以接受更高**：用户愿意等推理模型"思考"更长时间，时延约束放宽，但成本约束变严
- **KV Cache 压力倍增**：思维链 tokens 同样需要 KV Cache，超长思维链直接冲击内存上限

这推动了一批新的 serving 技术：KV Cache 分级存储（热数据在 GPU HBM，冷数据 offload 到 CPU RAM 或 SSD）、思维链流式输出（让用户感知到进度）、动态批次大小调整（避免长思维链请求阻塞短请求）。这些问题在 2024-2025 年是推理 serving 工程的核心挑战，尚未完全解决。

**参考**：[Speculative Decoding (arXiv 2211.17192)](https://arxiv.org/abs/2211.17192)

## 当前技术格局（截至 2026-05）

推理 serving 栈已经形成了清晰的分层：底层量化（AWQ/GGUF）负责内存压缩，vLLM/SGLang/TensorRT-LLM 等框架负责调度和批处理优化，推测解码提供 token 级加速，PD 分离处理大规模并发。对于 reasoning 模型，这套栈的每一层都面临新的适配需求。

## 关键分歧与未决问题

量化精度还能低多少？INT4 已经是主流，INT2 在特定任务上保持质量，但通用质量损失明显。是否有数学上的精度下限？

推理时扩展是否彻底改变了 serving 的经济学？如果用户为"thinking tokens"付费，serving 的优化目标从"最大化 QPS"变成"最大化每思维 token 的价值"——这是完全不同的工程问题。

边缘推理的上限在哪？量化 + 蒸馏 + 推测解码组合是否可以把 70B 级别的模型推到手机上？Apple 的 MLX 和高通的 AI Stack 在这个方向有积极探索。

## 对能力输出的影响

量化降低了模型可及性门槛，使更强的模型被更多人使用——这间接提升了所有能力维度的实际可及性。KV Cache 工程是长上下文能力从"理论支持"到"实际可用"的基础（百万 token 上下文在没有高效 KV 管理的情况下内存不可行）。推测解码主要提升速度而非能力，但在流式输出场景下改善了用户体验。

## 与其他轨道的交叉

- **architecture**：MoE 的推理特性（expert routing、expert 负载均衡）需要 serving 层专门支持；SSM 没有 KV Cache，推理内存模型完全不同
- **scaling**：推理时扩展是 scaling 理念的延伸，但它把"更多计算"的成本从训练时搬到了 serving 时
- **training**：蒸馏模糊了训练和推理优化的边界（用 serving 模型的输出作为训练数据）
- **data**：合成数据生成本身是一个推理 serving 负载，合成数据规模化需要高效推理基础设施
